# 底板和 USB-CAN 资料核查（2026-09-06）

结论：ATK-DLRK3506B V1.0 原理图已确认 12V 输入和两个 USB-A 下行接口；提供的 Linux SDK 只有 Intel x86/x86-64 库，不能直接部署到 RK3506B。当前没有实物枚举、电压或真实收发结果。

## 供电和接口：已由底板原理图确认

| 项目 | 图中证据 | 对本项目的影响 |
|---|---|---|
| 输入电压 | 第 3 页左上 `12V DCIN`，POWER1/DC-044A，1 脚进入 F1，2 脚接 GND，3 脚未接 | 名义 12V 输入已确认。核对实物同版本、插头尺寸和中心正外负极性后，现有 12V 2A 电源可作为供电候选；负载能力仍需验证。 |
| 板内转换 | 第 3 页 U2/SCT2230 将 VCC12V_DCIN 转为 VCC5V0_SYS，U4/SCT2230 再供 VCC_3V3 | 12V 只接 POWER1；禁止接 J1 的 5V、3V3、GPIO、USB VBUS 或 SN65HVD230。器件额定电流不能直接等同整板外供余量。 |
| USB 数据路径 | USB20_OTG1_DP/DM → U1/CH334R 上行 → HUB_DP1/DM1 和 HUB_DP2/DM2 → Dual USB A | USB-CAN 优先插底板双层 USB-A 其中一个，使用 A-to-C 数据线；host 运行状态仍由目标系统 `lsusb -t` 确认。 |
| USB 电源路径 | 两 USB-A 的 VBUS_T、VBUS_B 均接 VCC5V0_SYS | 该页没有画出逐端口限流电源开关；不能假设每口有独立过流保护。FB1 的 120R,2A 是磁珠标注，不能当作每口 2A 供电承诺，也不是 CAN 终端。 |
| J1 电源针 | 第 4 页 J1：1/17=3V3，2/4=5V；6/9/14/20/25/30/34/39=GND | 可用于核对电源轨；这里只把排针当测量点，不增加外设电源负载，也不从排针反向供电。 |
| J1 逻辑 | 3/5 为 I2C1 SDA/SCL，27/28 为 I2C0 SDA/SCL，图示 4.7k 上拉到 3V3；8=UART2 TX，10=UART2 RX | 上拉和布线已确认，不等于所有 GPIO 均耐 5V。GPIO 电压域、复用与 DS1302/继电器接法仍需核心板资料和设备树。 |
| 双网口 | 第 5/6 页分别为 YT8512C + HR911105A 的 NET0/NET1 | 已有百兆交换机/网线用途适配；物理 NET0/NET1 与 Linux 名称需实机映射，不能凭名字猜。 |

这份底板图没有给出 MIPI 屏连接器和核心板供电域的完整设计，不能用它确认屏排线接法、背光电流或核心板 USB Type-C 的具体用途。保持既有屏连接。

12V 2A 的 24W 是电源标称上限，不是测得的总机功耗。第一次仅接 RK+既有屏+USB-CAN；Nucleo 继续由 PC 的 ST-LINK USB 供电。测 POWER1 输入和 J1 电源轨在启动、点亮屏、插 USB-CAN 时是否稳定。未获厂商允许范围前，12V 11.4–12.6V、5V 4.75–5.25V、3V3 3.135–3.465V 仅作为保守台架排查目标，不代表板卡官方输入范围；超出时停止加负载并核对规格。DMM 不能捕捉全部短时跌落。

## 驱动：文件名和二进制交叉核验

| 库文件位置（解包后） | ELF class | e_machine | 结论 |
|---|---|---|---|
| x86/test/libusbcan.so | 1（32位） | 3 / EM_386 | Intel 32位，不是 ARM32 |
| x64/test/libusbcan.so | 2（64位） | 62 / EM_X86_64 | Intel/AMD 64位，不是 ARM64，更不是 RK3506 所需的 ARM32 |

RK3506 属 Cortex-A7 平台，依据 [Rockchip 官方产品页](https://www.rock-chips.com/a/en/products/RK35_Series/2025/1208/2126.html)。实际 Buildroot 用户态 ABI 仍须采集：ARM32 的软/硬浮点、glibc/musl/uClibc、动态加载器及依赖版本，不能仅索取一个笼统的“ARM版”。

Linux 包仅含 readme.txt、test.c、controlcan.h、Makefile、test 二进制和 libusbcan.so；未包含 libusbcan 实现源码、ARM 库或 SocketCAN 内核驱动。交叉编译 test.c 不能把 x86 动态库变成 ARM 库。静态字符串也显示 libusb-1.0.so.0、libstdc++.so.6、libpthread.so.0、libc.so.6 等引用，需要后续对新 ARM 库做实际依赖检查。

README 自称 libusb 实现，并标注 VID:PID 为 `0471:1200`；这是资料中声明的设备，不是已经读到的实物 ID。`controlcan.h` 使用 VCI_OpenDevice/VCI_InitCAN/VCI_Transmit/VCI_Receive API。按照该包的架构，它不注册 SocketCAN netdev，因此复制库不会产生 can0/can1；是否另有适配此实物的驱动尚未确定。[Linux SocketCAN 文档](https://docs.kernel.org/networking/can.html)说明的是 CAN 网络接口路线，与此库 API 不同。

## 厂商示例的验收陷阱

- README 示例的 TxType=2；test.c 明确将 2 解释为 self_test。这个输出不能证明远端 ACK 或 STM32 实收。
- 示例 `0x1400` 在 test.c 中标注为 1M，而项目 STM32 配置是 500k，不能照抄。
- 随机 ID 和数据用于它自己的 verify_frame 规则，不匹配本项目 0x123 → 0x321 协议。
- 原示例的 main 在 test() 失败后仍返回 0，因此 shell 退出成功不是 CAN 成功证据。

这些文件保留为参考，不把厂商例程当成已验证的验收程序。

## 接入路径与下一步

1. 在 RK 插入前后运行 [只读诊断脚本](../software/rk3506/collect-diagnostics.sh)，比较 VID:PID、接口、绑定驱动及用户态 ABI。脚本不装软件、不发帧、不配置接口。
2. 若已出现真实 SocketCAN netdev：按原 [SocketCAN 测试](../software/rk3506/README.md)验证对应端口和远端回复。
3. 若仅 USB 设备，使用厂商 VCI API：先取得匹配实物、ARM32 和当前 Buildroot ABI 的库或完整源码，再实现 CAN 采集后端。HMI 可以通过统一帧队列接 VCI 后端，但不能继续假定 candump 能直接读它。
4. 若无兼容 ARM SDK：先在匹配架构的 PC 上验证 USB-CAN 与 STM32，RK 集成仍标为阻塞。长期方案再选择有明确 ARM/Linux 6.1 SocketCAN 支持的设备，不凭“免驱”宣传判断。

目前资料仍不能确定 USB-CAN 现场 CAN_GND、隔离电源和 120Ω 开关的实际端子定义；沿用原接线表的条件限制，禁止从 ZLG 文件名推断其一定是正品 ZLG 或与已购设备完全匹配。

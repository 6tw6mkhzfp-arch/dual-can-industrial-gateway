# 厂商没有 ARM32 SDK 时的实施路线

前提：`USBCAN-UC12` 的 `0471:1200` 已在 RK 完成 USB 枚举，但当前固件没有真实 `can` 或 `tty` 接口；厂商旧 Linux 库只有 x86/x86-64，新增 ZIP 只有 Windows 驱动。没有协议或源码时，不能把 x86 库复制、重编译示例程序或仅添加 USB ID 就变成 ARM 驱动。

## 路线 A：保留现有设备，先完成物理 CAN 台架测试

用 Windows PC 安装与此型号匹配的驱动和上位机，USB-CAN 接 PC，与 NUCLEO-F103RB + SN65HVD230 进行单路请求/回复，再切换第二路。上位机须明确设备型号、500k、经典 CAN、正常模式；抓包要看到 MCU 的独立 0x321 回复和 0x100 心跳。此路线验证总线硬件，但不验证 RK 接入；Windows 驱动安装、编译烧录和真实总线测试尚未做。

## 路线 B：保留现有设备，增加常驻电脑作网络桥

在 x86-64 Linux 电脑或 USB 透传后的虚拟机上，核对旧 `libusbcan.so` 的依赖和 API 后，通过该库读写双通道 CAN，再通过有线网络把帧送到 RK HMI。需要设计断线/重连、帧时间戳、两个通道标识、发送授权、错误上报和开机自启。此路线依赖电脑常驻运行，不满足“RK 单机直连双 CAN”的最终目标；库及 USB 透传也尚未实测。

## 路线 C：更换有明确 Linux 支持的双通道 USB-CAN

若最终目标必须是 RK 单机运行，选择前要求卖家提供**该精确硬件修订版和 VID:PID** 在 Linux 6.1/ARM32 上的驱动源码、内核配置方法或标准 SocketCAN 支持证据，最好有 `ip -details link show` 的两个真实接口实测。不能仅凭“支持 Linux”、接口为 Type-C 或芯片外形判断兼容。替换后还需核对隔离地、终端电阻、供电和 Linux 6.1 构建条件。

当前建议：先走 A 验证已购硬件及 STM32 接线；同时向卖家索取源码。若卖家明确没有，且不能接受常驻电脑，则按 C 的验收条件选型。真实 CAN 收发仍待测试。
